# getmes-tg

> Утилита на Node.js для выгрузки истории Telegram-каналов: в Markdown-файлы и/или в MySQL, а также для отправки сообщений и файлов в чаты через Telegram API (gramjs).

[![Node.js 18+](https://img.shields.io/badge/Node.js-18%2B-339933.svg)](https://nodejs.org)
[![Telegram API](https://img.shields.io/badge/Telegram-API-26A5E4.svg)](https://core.telegram.org/api)

> ⚠️ Два параллельных запуска одного режима не поддерживаются (общие `state/` и `output/` → дубли): контейнерный cron и ручные запуски выполняйте по очереди — перед ручным запуском `docker compose stop app`, после `docker compose start app`.

## Возможности

- **`export`** — инкрементальная выгрузка истории каналов в `output/*.md` (новые сообщения дописываются в конец, дублей нет).
- **`db`** — выгрузка **только** в MySQL: авто-создание таблицы, идемпотентный upsert, хранение названия канала, ссылки на сообщения.
- **`full`** — комплексная выгрузка: `output/*.md` и MySQL за один проход — один вход в Telegram, одна пагинация на канал, независимые чекпоинты обоих режимов.
- **`send`** — отправка сообщений и/или файлов в чат по `id`/`@username` (в т.ч. `--chat me` — «Избранное»).
- **Прокси** — подключение к Telegram через SOCKS5/SOCKS4 с авторизацией login/password либо прямое соединение; настройка в файле конфигурации (секция `proxy`), без перекомпиляции и флагов командной строки.
- **Бинари** — самодостаточные исполняемые файлы под 3 x64-платформы (Windows/Linux/macOS; сборки arm64 в `Makefile` закомментированы) на runtime Bun: на целевой машине не нужен ни Node.js, ни `node_modules`.

## Требования

- Node.js 18+ (для запуска из исходников) **или** готовый бинарь из `dist/`.
- Аккаунт Telegram и `apiId`/`apiHash` с [my.telegram.org](https://my.telegram.org).
- MySQL 8+ — только если нужен режим `db`.

## Быстрый старт

```bash
npm install
```

1. Создайте `config.yaml`: скопируйте шаблон без секретов и заполните его — `cp config.yaml.example config.yaml` (секции `api` и `channels` обязательны, подробности — в [Конфигурация](#конфигурация)). Если файла нет или в нём синтаксическая ошибка, приложение не упадёт со стектрейсом, а аккуратно сообщит и завершится с кодом 1:
   ```
   Ошибка: файл конфигурации не найден: config.yaml — создайте его или укажите путь через --config <путь>
   Справка:  export.js help
   ```
2. Первый запуск — пройдите интерактивный вход (телефон → код → пароль 2FA при необходимости):
   ```bash
   node export.js export
   ```
   Готовая сессия сохранится в `session.txt` — следующие запуски без диалогов.
3. Дальнейшие запуски инкрементальны: берутся только сообщения после последнего выгруженного. Прогресс каждого режима хранится в `state/` — см. [Чекпоинты (state/)](#чекпоинты-state); `config.yaml` при работе не изменяется.

## Команды

| Команда | Что делает |
|---|---|
| `node export.js` / `help` | Справка по всем параметрам |
| `node export.js export [--channel <id\|заголовок>] [--repair] [--config <путь>]` | Выгрузка в `output/*.md` (или `npm run export`) |
| `node export.js db [--channel <id\|заголовок>] [--repair] [--config <путь>]` | Выгрузка **только** в MySQL |
| `node export.js full [--channel <id\|заголовок>] [--repair] [--config <путь>]` | Комплексная выгрузка: `output/*.md` **и** MySQL за один проход |
| `node export.js send --chat <id\|@username> (--text "..." \| --text-file <путь>) [--file <путь>] [--plain]` | Отправка сообщения и/или файла |

Полный список флагов: `node export.js help`.

**`--repair` (полная сверка, у `export`, `db` и `full`).** Игнорирует чекпоинты и заново проходит канал с `startDate`:

- `export --repair` — из файла берётся множество id, в конец дописываются **только отсутствующие** сообщения (дубли невозможны: сверка по id), затем state-запись выравнивается с вершиной файла.
- `db --repair` — полная выборка с `startDate` + штатный идемпотентный upsert (`ON DUPLICATE KEY UPDATE`): дублей не создаётся, чекпоинты каналов обновляются.
- `full --repair` — обе сверки за один проход: файл доливает отсутствующие id, БД — полный upsert (см. «Комплексный экспорт»).
- Ограничение: доливка идёт **в конец файла** — у долитанных сообщений даты могут «перескочить» (порядок остальных не меняется). Тяжёлая операция, объём ограничивается `startDate`; запускайте осознанно, вручную.

## Конфигурация

Основной файл — `config.yaml` рядом с программой:

```yaml
api:
  apiId: 123456
  apiHash: "..."
  sessionFile: session.txt

db:
  driver: mysql
  host: 127.0.0.1
  port: 3306
  user: root
  password: "..."
  database: tgexport

channels:
  - id: "-1001149896996"
    title: Интерфакс
    startDate: "2026-09-30T00:00:00Z"

log:
  dir: ./logs
  level: info
  fileMask: getmes-tg_{date}.log

proxy:
  enabled: false           # true — подключаться через прокси, false — напрямую
  host: "176.108.243.232:10808"
  username: "user"
  password: "..."
```

- `api` — обязателен; `apiId`/`apiHash` берутся с my.telegram.org.
- `db` — обязателен только для подкоманды `db`.
- `channels` — список каналов: `id` (супергруппы вида `-100...` или `@username`), `title` (для заголовков и названия в БД), `startDate` (граница истории при первичной заливке).
- `log` — необязателен (работают дефолты): `dir` — каталог логов (создаётся сам), `level` — `debug | info | warn | error | silent`, `fileMask` — имя файла, `{date}` заменяется на дату `YYYY-MM-DD`.
- `proxy` — необязателен; при отсутствии секции или `enabled: false` — прямое подключение (см. [Прокси](#прокси-socks5)).
- Чекпоинты выгрузки в конфиг **не пишутся**: `config.yaml` только читается, секреты в нём не переписываются ни одним запуском. Прогресс каждого режима хранится отдельно, в `state/` (см. [Чекпоинты (state/)](#чекпоинты-state)). Старые поля `lastMessageId`/`lastMessageUrl`, если они остались в файле, игнорируются — их можно удалить руками.

**Отключение опций:**

```yaml
log: false        # или log: { enabled: false } — без лог-файлов и каталога logs/
                  # (консоль показывает всё, включая шум gramjs)
db: false         # или db: { enabled: false } — подкоманда db завершится
                  # понятной ошибкой до подключения к Telegram и базе
proxy: false      # или proxy: { enabled: false } — прямое соединение с Telegram
```

> ⚠️ `config.yaml` (API-ключи, пароль БД, пароль прокси) и `session.txt` (живая сессия) — секреты. Не публикуйте их; в `.gitignore` они уже исключены. Формат определяется расширением: `.yaml`/`.yml` — YAML, `.json` — JSON; без `--config` ищется `config.yaml` → `config.yml` → `config.json` (старый JSON-конфиг остаётся рабочим).

Путь к конфигу можно переопределить флагом `--config <путь>`.

### Чекпоинты (state/)

Прогресс режимов хранится в двух **независимых** файлах — по одному на режим:

| Файл | Режим |
|---|---|
| `state/export.yaml` | выгрузка в `output/*.md` |
| `state/db.yaml` | выгрузка в MySQL |

Запись выглядит так (карта по `channelId` канала):

```yaml
"-1001149896996":
  title: Интерфакс
  lastMessageId: 79644
  lastMessageUrl: https://t.me/c/1149896996/79644
```

- **Полная независимость режимов:** каждый читает и пишет только свой файл, поэтому утилиту можно использовать только для файлов, только для БД или для обоих сценариев, а одновременный запуск `export` и `db` безопасен (два параллельных запуска **одного** режима не поддерживаются). Комплексный режим `full` — исключение по сути, а не по устройству: он соблюдает правила обоих режимов, но пишет **оба** файла (см. «Комплексный экспорт») — одновременно с тиком cron его не запускайте ни с каким режимом.
- **`title` (название канала)** — первым полем каждой записи, только для читаемости файла: на логику чекпоинтов не влияет. Старым записям название проставляется автоматически при первом запуске режима на новой версии, изменение названия канала в конфиге подхватывается при следующем запуске.
- **Правило чекпоинта:** `max(state-запись, состояние артефакта)` — для `export` это вершина `output/<канал>.md`, для `db` — `MAX(message_id)` по каналу. Поэтому аварийный обрыв или потеря `state/` не ведут к дублям: чекпоинт восстанавливается из самого результата выгрузки. Если БД по каналу пуста, `db` делает первичную заливку с `startDate`.
- **Пропустить часть истории** (ручной «подъём») — увеличьте `lastMessageId` нужного канала в соответствующем state-файле.
- **Долить накопившиеся пропуски** — `export --repair` / `db --repair` / `full --repair` (полная сверка с `startDate`, см. «Команды»): чекпоинты игнорируются, недостающее дописывается без дублей.
- **Пересобрать канал заново** — удалите его артефакт **и** запись из state: файл `output/<канал>.md` (для `export`) либо строки канала в таблице `messages` (для `db`). Удаление только артефакта при оставшейся записи дозальёт лишь сообщения новее записи.
- Каталог `state/` создаётся автоматически и исключён из git (как `output/` и `logs/`). Повреждённый state-файл даёт понятную ошибку с инструкцией: удалите его — чекпоинт восстановится из артефакта.

## Прокси (SOCKS5)

Все соединения с Telegram (выгрузка, отправка, выгрузка в БД) идут через один настраиваемый SOCKS-прокси. Настройка — **только в файле конфигурации**, флагов командной строки нет.

### Включение и выключение

```yaml
# Прокси ВКЛЮЧЁН — все подключения к Telegram идут через него
proxy:
  host: "176.108.243.232:10808"   # адрес:порт прокси-сервера
  username: "user"                 # логин (необязательно, если прокси без авторизации)
  password: "..."                 # пароль (необязательно)
```

```yaml
# Прокси ВЫКЛЮЧЁН — прямое подключение (один из трёх вариантов)
proxy: false                      # вариант 1
proxy:
  enabled: false                  # вариант 2 (секция сохранена, но не используется)
  host: "176.108.243.232:10808"
# вариант 3 — секции proxy нет в файле вовсе
```

Правило: **нет секции / `proxy: false` / `enabled: false` → прямое соединение; секция с `host` есть и не выключена → через прокси.**

### Поля секции `proxy`

| Поле | Обязательно | По умолчанию | Описание |
|---|---|---|---|
| `host` | да* | — | Прокси-сервер. Форматы: `"ip:порт"` одной строкой (рекомендуется), либо `"ip"` + отдельное поле `port`, либо IPv6 в скобках `"[::1]:1080"`. *Не обязательно, только если задан `enabled: false` |
| `port` | нет | из `host` | Порт 1–65535; нужен, если в `host` порта нет |
| `username` | нет | — | Логин SOCKS-авторизации |
| `password` | нет | — | Пароль SOCKS-авторизации |
| `enabled` | нет | `true` | `false` — полностью игнорировать секцию (работа напрямую) |
| `socksType` | нет | `5` | Версия протокола: `5` или `4` |
| `timeout` | нет | `5` | Таймаут подключения к прокси, секунд |

Формат `host: "адрес:порт"` в YAML без кавычек тоже работает, но с паролями/логинами рекомендуются кавычки — спецсимволы вида `:`, `#`, `{` иначе YAML может неверно разобрать.

### Что происходит при работе

- Ошибки конфигурации прокси (`нет host`, `нет порта`, `порт вне 1–65535`, `socksType: 9` и т.п.) выводятся как `Ошибка: ...` **до входа в аккаунт** — приложение не пытается логиниться с кривой настройкой.
- При включённом прокси в лог пишется строка `прокси: включён, SOCKS5 176.108.243.232:10808` (без пароля).
- Если прокси недоступен или не пропускает трафик к Telegram, после 5 попыток выводится `Критическая ошибка: не удалось подключиться к Telegram через прокси SOCKS5 <адрес> за 5 попыток — ...` и программа завершается с кодом 1. Все 5 попыток длятся около 30–40 секунд — это нормально.
- Сырые ошибки ретраев gramjs (`SocksClientError: Proxy connection timed out` с трейсом) в консоль **не выводятся** — на время подключения они уходят только в лог-файл; в консоли остаётся лишь итоговое сообщение выше. (Диагностика: смотрите `logs/`.)
- **Важно:** прокси-сервер должен разрешать соединения к серверам Telegram (`149.154.167.50:80`, `149.154.167.50:443`, `91.108.56.100:443` и др. из списков DC). Прокси может откликаться и принимать авторизацию, но блокировать именно диапазоны Telegram — тогда подключение не установится, хотя другие сайты (например, google.com) через этот же прокси открываются. Проверить можно, временно включив `enabled: true` и запустив `export` — при успехе появятся обычные строки выгрузки.

### Примеры

```yaml
# SOCKS5 без авторизации
proxy:
  host: "10.0.0.1:1080"
  enabled: true

# SOCKS4 с логином, кастомный таймаут
proxy:
  host: "10.0.0.1"
  port: 1080
  socksType: 4
  username: "user"
  timeout: 15
```

## Логирование и вывод

- **Консоль — компактно:** по одной строке на канал, одна итоговая и строки ошибок — пример ниже.
- **Подробности — в лог-файл:** `logs/getmes-tg_2026-10-04.log` — авторизация, прогресс по страницам, чекпоинты, предупреждения gramjs, а также работа с базой: `MySQL: соединение с ... установлено`, `канал «Интерфакс»: новых сообщений 4, вставлено в MySQL 4`.
- **Ротация:** имя файла содержит дату записи, поэтому с наступлением нового дня первая запись создаёт новый файл — один лог-файл на один день, без таймеров.
- Уровень `log.level` фильтрует записи в файл; предупреждения и ошибки дублируются в консоль независимо от него.
- **Выключить логи совсем:** `log: false` (или `log: { enabled: false }`) — ни файлов, ни каталога `logs/`; консоль показывает полный вывод, включая `[INFO]` gramjs.

Пример вывода (значения — из живых прогонов):

```text
РИА Новости: +76 → output/РИА Новости.md (#347383)   ← строка на канал: сколько новых сообщений, файл выгрузки, id последнего из них
MarketTwits: нет новых                              ← после чекпоинта изменений нет — ничего не записывается
Готово: 8 каналов, +179 сообщений за 2.7 с          ← итоговая строка: число каналов, суммарный прирост, длительность
! Интерфакс: <текст ошибки>                          ← ошибка канала не прерывает выгрузку остальных
```

## Выгрузка в MySQL

```bash
node export.js db                    # все каналы
node export.js db --channel Интерфакс # один канал
```

- Схема создаётся автоматически: таблица `messages` с `PRIMARY KEY (channel_id, message_id)`.
- Повторный запуск не создаёт дублей (`ON DUPLICATE KEY UPDATE`).
- Хранятся: `channel_title` (название канала, старые строки дозаполняются бэкфиллом), отрендеренный Markdown, сырой текст, JSON сущностей, `media_class`, ссылка на сообщение.
- Первый запуск по каждому каналу заливает историю с `startDate`; далее — только новое.
- Чекпоинт берётся из `MAX(message_id)` по каналу и `state/db.yaml` (правило `max`, см. «Чекпоинты (state/)»).
- `node export.js db --repair` — полный реимпорт с `startDate` без дублей: существующие строки обновляются, недостающие вставляются, инвариант `COUNT(*) = COUNT(DISTINCT channel_id, message_id)` сохраняется.

## Комплексный экспорт (full)

`node export.js full` — третий режим, совмещающий `export` и `db` за один запуск: один вход в Telegram и **одна пагинация на канал** вместо двух (паузы 500 мс между страницами — один раз на канал):

```bash
node export.js full                  # все каналы: output/*.md + MySQL за один проход
node export.js full --channel РИА    # один канал
node export.js full --repair         # полная сверка обоих режимов за один проход
```

- **Один fetch, два чекпоинта.** Канал читается от `min(cpExport, cpDb)` (нулевой чекпоинт — например, пустая БД — даёт полную выборку с `startDate`), дальше выборка делится: в файл идут только сообщения новее чекпоинта файла, в БД — новее чекпоинта БД. Расхождение чекпоинтов (один режим впереди) закрывается автоматически: отставший догоняет, продвинутый не получает чужих строк и дублей.
- **Каждый режим — со своими правилами:** чекпоинт файла `max(state, вершина файла)`, чекпоинт БД `max(state, MAX(message_id))`; порядок «артефакт → state» соблюдается для каждого артефакта отдельно.
- **Независимые ошибки:** падение файловой части не отменяет выгрузку в БД и наоборот (строка канала выглядит как `файл: ошибка | MySQL +2 (...)`). Чекпоинт режима не двигается при его ошибке — следующий запуск доделывает без дублей. Если ошибла хотя бы одна часть, **код выхода — 1** (в одиночных `export`/`db` ошибки каналов код не меняют — их поведение не тронуто).
- **`full --repair`** — чекпоинты игнорируются, одна полная выборка с `startDate`: файл доливает отсутствующие id (сверка множества, как в `export --repair`), БД — полный идемпотентный upsert. Ограничение с «перескочком» дат — то же.
- ⚠️ **Совместимость с cron:** `full` пишет **оба** state-файла, поэтому с тиком контейнерного cron он несовместим ни в каком сочетании: перед запуском `docker compose stop app`, после — `docker compose start app`. Два параллельных запуска `full` тоже не поддерживаются.

## Отправка сообщений

```bash
node export.js send --chat me --text "привет"
node export.js send --chat @username --text-file msg.md
node export.js send --chat -1001234567890 --file photo.jpg --plain
```

- `--plain` — отправить текст дословно, без разбора Markdown (встроенный парсер gramjs не понимает ссылки вида `[текст](url)`).
- Валидация параметров выполняется до входа в аккаунт: опечатка в команде не логинит клиента.

## Сборка бинарей

Нужен [Bun](https://bun.sh) (≥1.4). Windows без `make` — команды вызываются напрямую, они же в `Makefile`:

```bash
bun build ./export.js --compile --target=bun-windows-x64 --outfile dist/getmes-tg-windows-x64.exe
```

| Цель | Платформа |
|---|---|
| `make windows` | Windows x64 (.exe) |
| `make linux` | Linux x64 |
| `make macos` | macOS Intel |
| `make` | все три сразу |
| `make clean` | удалить `dist/` |

Сборки под arm64 (`windows-arm64`/`linux-arm64`/`darwin-arm64` и алиасы `windows-arm`/`macos-arm`) **закомментированы в `Makefile`** — чтобы вернуть, раскомментируйте соответствующие цели, включите их в `TARGETS` и строки `.PHONY`.

Бинарь запускайте **из каталога, где лежат `config.yaml` и `session.txt`** — он ищет их в рабочем каталоге.

## Раскатка в Docker

Самодостаточный стек из двух сервисов: контейнер приложения (busybox **crond, задачи каждые 3 минуты** — `export` в `output/*.md` и `db` в MySQL) + изолированный MySQL 8 в общей сети (порт наружу не публикуется). Образ — двухстадийная сборка на Alpine, **184 MB**; конфиг, сессия, `output/`, `state/` и `logs/` монтируются с хоста и в образ не попадают (секреты исключены и `.dockerignore`).

Подготовка (один раз):

```bash
# 1. конфиг для контейнера — копия config.yaml с db.host: mysql
sed 's/host: 127.0.0.1/host: mysql/' config.yaml > config.docker.yaml
# 2. пароль MySQL для сервиса mysql (равен db.password в config.docker.yaml)
#    — лежит в .env (шаблон: .env.example)
# 3. сессия должна быть файлом (пустой файл — при первом запуске пройдёт
#    интерактивный вход)
touch session.txt
```

```bash
docker compose up -d --build            # поднять: cron */3, оба режима
docker compose logs -f app              # вывод cron-задач
docker compose run --rm app node export.js help    # разовый запуск любой команды
docker compose run --rm app node export.js export # выгрузить сейчас же, не дожидаясь тика
docker compose down                     # остановить (volume mysql-data остаётся)
docker compose down -v                  # остановить и удалить базу
```

- Переключатели в `docker-compose.yml` (или `.env`): `RUN_EXPORT=0/1`, `RUN_DB=0/1`, `CRON_SCHEDULE` (по умолчанию `*/3 * * * *`), `TZ`.
- ⚠️ **Чекпоинты общие с хостовыми запусками** (`state/`, `output/` — те же bind-тома, что файлы на хосте), поэтому одновременный запуск контейнерного и «ручного» **одного** режима делать нельзя: перед ручным запуском остановите cron — `docker compose stop app`, после — `docker compose start app`. Файлы создаются от uid 1000 (пользователь `node`) — на хосте остаются ваши.
- Вывод cron-задач идёт в `docker compose logs app` и дублируется в `logs/cron-console.log`, служебные строки crond — в `logs/crond.log`; подробности каждого запуска — в `logs/getmes-tg_*.log`, как обычно.
- Если предыдущий тик ещё работает (долгая первичная заливка), следующий его пропускает — два параллельных запуска одного режима не поддерживаются.
- ⚠️ **После `docker compose build` обязательно пересоздайте контейнер** — `docker compose up -d app` (или `up -d --build`): работающий контейнер продолжает выполнять **старый образ**, пока его не пересоздадут (проверка: `docker inspect getmes-tg --format '{{.Image}}'` должен совпадать с `docker images -q getmes-tg`).
- Доступ к базе с хоста: `docker compose exec mysql mysql -uroot -p tgexport`.
- Первая заливка в пустую базу — с `startDate`, поэтому после `down -v` база наполняется заново.

## Подводные камни

- Чекпоинты считаются как `max(state-запись, артефакт)`: обрыв между записью файла канала и записью в `state/` не создаёт дублей (берётся вершина файла), а потерянный `state/` восстанавливается из `output/*.md`/`MAX(БД)`.
- Сброс чекпоинта — только через артефакт: удалить `output/<канал>.md` (или строки канала в `messages`) **и** запись в `state/`. Устаревшие поля `lastMessageId` в конфиге ничего не делают: удаление только их выгрузку не пересоберёт.
- ⚠️ **Контейнерный cron и ручные запуски делят `state/` и `output/`** — это одни и те же bind-тома, что файлы на хосте. Два параллельных запуска **одного** режима не поддерживаются нигде, а lock-и контейнера хостовым запускам не мешают (они живут в `/tmp` контейнера), поэтому пока идёт тик в контейнере, ручной `export`/`db` не запускайте — и наоборот. Перед ручным запуском: `docker compose stop app`, после: `docker compose start app`. Разные режимы (`export` + `db`) между собой параллельны в любом сочетании.
- Инкрементальность держится на `minId`: `offsetId` в gramjs ведёт к более старым сообщениям и дублирует выгруженное.
- Текст берётся из `msg.rawText` — `msg.text` в gramjs уже отрендерен как Markdown, наложение сущностей поверх него портит вывод.
- Завершение клиента — только `client.destroy()`: обычный `disconnect()` подвешивает процесс на ~30 с.
- `client.connect()` при неудаче **возвращает `false`, а не бросает** — без явной проверки результата `client.start()` зависает на мёртвом соединении, промис утекает и процесс молча завершается с кодом 0. Именно поэтому в `lib/session.js` результат `connect()` проверяется явно (так проявился баг при недоступном прокси).
- Прокси настраивается только в конфиге: `enabled: false` — прямое соединение, включение без валидного `host` — понятная ошибка до входа в аккаунт. SOCKS-пароль в логи и вывод не пишется.
- Имена файлов в `output/` — на кириллице; в консоли PowerShell без UTF-8 они отображаются как кракозябры (это только вывод, файлы в порядке).
- Пауза 500 мс между страницами защищает от FloodWait — не убирать.
- Вывод намеренно сокращён: детали ищите в `logs/`, а не в консоли. Сообщения об ошибках и справка называют программу по имени файла (`export.js` или имя бинаря) — без `node`, т.к. бинарю он не нужен.
